# 过拟合归因：是哪个部件提供了记住训练集的条件

日期：2026-09-02

## 结论先行

1. **过拟合不来自容量，来自新增的信息通路。** 三个 20M adapter 的 train-dev BLEU-4 差距相差
   十倍，而参数量几乎相同——且**过拟合最轻的基线，projection 反而最大**。
2. **融合块本身不记忆，projection 在记。** 6k 步内融合各编码器的权重范数只动 +0.3~0.6%，
   projection 动了 +3.3%。
3. **融合提供的信息被不成比例地用于拟合训练集。** 把 gate 从 0.56 微调到 0.50，
   **train 的损失涨幅是 dev 的 1.85 倍**。这是本文档唯一的直接因果证据，前两条是间接的。
4. **但这个不对称主要是过拟合的*结果*，不是原因**（见 3.2 节）。它在过拟合之前就存在
   （+0.187），随过拟合翻了一倍多（+0.490）。融合分支不是凭空造出过拟合，而是提供了
   一条会被越用越偏的通路。
5. **两条流的角色不同，而且随时间反转**：运动流的不对称是结构性的、一开始就在、几乎不增长；
   content 流的是学出来的、随过拟合快速膨胀。**只看终态会把结果误认成起因**——本文档
   3.1 节就犯过这个错。
6. **位移流关掉后损失一动不动**（±0.01），它占的 0.9% 就是它的真实价值。

合起来的机制：**融合让视频变得可区分，projection 把区分度换成句子；而 content 流——那条
对同一个 x 的冗余再变换——是这个过程随训练主要膨胀的通道。**

---

## 1. 容量不是原因

| run | adapter | projection rank | train-dev gap @30k |
| --- | --- | ---: | ---: |
| pooled-linear 基线 | 全局均值 | **5385（最大）** | **+0.004** |
| hand-ROI concat | 全局均值 + ROI 均值 | 4109 | +0.031 |
| next-frame fusion | 融合后全局均值 | 4429 | **+0.043** |

三者都是 ~20M 参数。基线的 projection 比另外两个都大，却几乎不过拟合。**gap 跟的是每个
adapter 多引入的那条输入通路，不是它有多少参数。**

## 2. 权重范数：融合冻住，projection 在长

从 checkpoint 直接算，按部件聚合 L2 范数：

| run（步数区间） | 部件 | 起 | 止 | 增长 |
| --- | --- | ---: | ---: | ---: |
| next-frame (36k→42k) | projection | 78.48 | 81.09 | **+3.3%** |
| | fusion.delta_encoder | 45.79 | 45.93 | +0.3% |
| | fusion.content_encoder | 42.34 | 42.60 | +0.6% |
| | fusion.fusion_output | 24.20 | 24.27 | +0.3% |
| | fusion.displacement_projection | 1.82 | 1.86 | +2.1% |
| | fusion.fusion_gate | 0.19 | 0.24 | +27.9%（绝对值极小）|
| baseline (36k→48k) | projection | 79.89 | 85.42 | +6.9% |
| handroi (24k→30k) | projection | 67.38 | 72.49 | +7.6% |

**局限**：权重范数是弱代理，模型可以靠旋转方向记忆而不增大范数；三个 run 处在不同训练
阶段，而权重增长本来就会随训练减速，所以**跨 run 的增长率不可比**（handroi 看着最快，但它
最早）。这一节只支持"在 next-frame 内部，projection 比融合活跃得多"，不支持更多。

## 3. Gate 消融：直接证据

`experiments/diagnose/gate_ablation.py`，checkpoint = next-frame wr3/hardmatch @42k，
train / dev 各 200 个 batch 的 teacher-forced CE：

| | 原样 σ=0.56 | σ=0.5 | σ=0（全关）|
| --- | ---: | ---: | ---: |
| train | 0.9174 | 1.9429 (**+1.026**) | 6.3508 (+5.433) |
| dev | 2.0460 | 2.6002 (**+0.554**) | 6.2795 (+4.234) |
| **train − dev 涨幅差** | | **+0.471（1.85×）** | +1.200（1.28×）|

**读数看 σ=0.5 那一档，不是全关那档。** 全关时两边都涨到 ~6.3，接近无条件语言模型的水平，
模型已经坏透，要测的差异被饱和压平（倍数从 1.85 掉到 1.28）。**只测全关会低估这个效应**——
脚本里的 `--gate-values` 就是为此加的。

## 3.1 分流消融：捷径来自**静态外观流**，不是运动

第 3 节关掉的是整条融合分支。但融合把三条流求和成 update，其中两条量级相当：
**content**（对同一个 `x` 的第二次可学习变换，而 `x` 本来就在残差路径上加回去）占融合隐向量
的 69%，**delta**（真正新增的时间信号）占 74%。关 gate 是把两条一起关掉，分不出是谁。

`--streams` 用 forward hook 把某条流的输出单独置零（**gate 保持原样**），同一个 checkpoint、
同样 200 batch：

| 设置 | train 涨 | dev 涨 | train − dev |
| --- | ---: | ---: | ---: |
| sigmoid=0.5 | +1.044 | +0.554 | +0.490 |
| sigmoid=0（全关）| +5.448 | +4.234 | +1.215 |
| **no-content**（关静态流）| **+4.042** | +2.910 | **+1.133** |
| **no-delta**（关运动流）| +2.074 | +1.135 | +0.939 |

**关掉 content 造成的 train-dev 不对称（1.133）比关掉 delta（0.939）更大，绝对影响也大得多
（+4.04 vs +2.07）。**

**所以"运动分支产生了运动捷径"这个假说不成立，至少不是主因。** 融合里被拿去拟合训练集最多
的是 `content_encoder`——一条**信息上完全冗余**（`LN(x)` 的 `x` 就是残差加回去的那个 `x`）、
只增加容量的通路。这正是"增加容量但不增加信息"的形态。

修正后的机制：**过拟合的条件主要来自融合块给静态特征加的那条额外变换通路。** 第 3 节末尾
那句"融合把高熵的视频特有运动信号注入池化向量"被本节推翻。

**本节的局限**：两条流关闭后剩余的量级并不严格相等（74% vs 69%），而 `/√3` 的缩放是固定的，
所以两者不完全可比。这个差别不足以解释 1.133 vs 0.939，但精确归因需要做尺度补偿，**没做**。

## 3.2 时间维度：不对称是结果，不是原因

3 和 3.1 节都只测了 42k 那一个 checkpoint，而它的 BLEU-4 gap 已经 +0.1055，深度过拟合。
在同一架构的 gate1 run 的 18k / 24k 两个 checkpoint 上重跑同一个脚本（那两点 gap 分别是
**−0.0098** 和 **+0.0143**，即尚未 / 刚开始过拟合）：

| | BLEU-4 gap | σ=0.5 的 train−dev | no-content | no-delta | no-displacement |
| --- | ---: | ---: | ---: | ---: | ---: |
| gate1 @18k | −0.0098 | +0.187 | +0.119 | **+0.251** | −0.009 |
| gate1 @24k | +0.0143 | +0.374 | +0.407 | +0.248 | +0.008 |
| gate0 @42k | +0.1055 | +0.490 | **+1.133** | +0.939 | 未测 |

**三条结论：**

**① 不对称随过拟合单调增长（0.187 → 0.374 → 0.490），所以它主要是过拟合的结果。**
但它在 18k 就已经有 +0.187，而那时 BLEU-4 上 train 还不如 dev——**结构性的底子是存在的**，
只是大头是长出来的。

**② content 与 delta 的排序随时间反转。** 18k 时 delta 的不对称是 content 的两倍多
（0.251 vs 0.119），24k 反转，42k content 大幅领先。而 `no-delta` 的值在 18k→24k 几乎不动
（0.251 → 0.248）。读法：**运动流的偏差是结构性的、固定的；content 流的偏差是学出来的、
随过拟合膨胀。**

**这修正了 3.1 节。** 那里说"捷径来自 content 流"，是只看 42k 一个点得出的——把终态误认成
了起因。更准确的表述在本节 ② 里。

**③ 位移流没有携带有用信息。** 关掉它两个 split 的损失都在 ±0.01 内（噪声量级）。占 0.9%
就是它的真实贡献，不是"被初始化压制了"。

## 4. 对设计的结论

- **空间 dropout 的位置是对的**：它卡在融合和 projection 之间，削弱到达 projection 的信息。
- **但可能不够**。被滥用的是融合的*输出*，而空间 dropout 只是随机丢 patch，剩下的 patch
  照样把 content 流的那份冗余容量送过去。
- **优先级最高的那处是 `projection` 的隐层**（GELU 之后、第二个 Linear 之前）：它是最大的
  部件（16.4M，占 82%）、唯一在增长的部件、也是进 LLM 前的最后一道。
- **融合内部若要加 dropout，加在 `content_encoder` 上**，依据是 3.2 节 ②：它是随过拟合
  膨胀的那条通路，正是正则化该约束的对象。delta 流的偏差固定不长，dropout 约束不到它。
  注意这和第 2 节不矛盾：权重范数说融合**自己不记忆**，3.1/3.2 说它**给 projection 喂了
  可记的东西**——前者是"谁在长"，后者是"谁提供了条件"。
- **位移流的 kaiming 初始化：期望调低。** 3.2 节 ③ 显示这条流在当前形态下不携带有用信息，
  所以把它从 0.9% 抬到 15.2% 未必换来什么。仍值得跑一次（零初始化下它从没得到过机会），
  但如果没变化，答案是"位移这个特征没用"，而不是"初始化不对"。
- 建议 **projection dropout + 空间 dropout 一起上**，而不是只做一个。

### 关于 dropout 放在哪里的一个实现约束

`fusion_output` 末尾是 `LayerNorm(D, elementwise_affine=False)`，它把 update 的模长钉死在
√D。后果是：**在 `content_hidden` 上做逐元素 dropout，"减弱幅度"的效果会被这个 LayerNorm
基本抵消**——隐向量变了，但 update 的模长仍被拉回原值，只剩方向扰动。

如果目标是"别依赖 content 流"，正确形式是 **stream-level 的随机整体丢弃（drop-path 语义）**：
逐样本地以概率 p 把整条 `content_hidden` 置零，强迫那部分样本的 update 只从 delta +
displacement 算出来。这与消融时用的 hook 是同一种语义，训练时施加的正是测量时施加的东西。
不需要 `1/(1-p)` 缩放——下游 LayerNorm 会把它吃掉。

同一个 LayerNorm 也是 3/3.1 节读数的局限来源：关掉任一条流不是"减去它的边际贡献"，而是
"用一个方向很不同的隐向量重算 update 再归一化回同样模长"。两条流受同样影响所以可比，
**但单个数字不能读成贡献量**。

## 5. Caveats

- ~~这个 checkpoint 已经深度过拟合，观察到的不对称可能是结果而非原因。这个实验还没做。~~
  **已做，见 3.2 节：主要是结果，但有结构性底子。** 用的是 gate1 run 的 18k/24k，不是同一个
  run 的更早步——gate0 run 只保留了 36k/42k（`save_total_limit: 2`）。两个 run 除
  `gate_init` 外配置相同，但严格说这是跨 run 比较。
- 第 3 节测的是 teacher-forced CE，不是 BLEU。两者通常同向但不等价。
- 只在 next-frame 这一个 adapter 上做过。hand-ROI 的两条通路（global / ROI）没有测过各自的
  依赖度，虽然脚本支持（它按名字找所有标量 gate，gated 融合模式下的 `fusion_gate` 也能测）。
- **`--streams` 的关闭并非等量**：三条流关掉后剩余的量级不同（74% / 69% / 0.9%），而 `/√3`
  的缩放是固定的。这个差别不足以解释 3.2 节 ② 的反转（那是时间趋势，不是绝对值比较），
  但精确归因需要尺度补偿，**没做**。
- **token 置换检验没做**（`permute_video_tokens` 就在 adapter 签名里）。它回答的是更根本的
  问题：模型到底有没有在用时序结构。
- LLM 和 backbone 全程冻结，所以记忆只可能发生在 adapter 内——这条前提让归因范围小到
  20M 参数，换成可训练 LLM 时全部结论都要重做。

## 6. 复现

```bash
python experiments/diagnose/gate_ablation.py \
    --checkpoint <run>/checkpoint-42000 \
    --batches 200 \
    --out outputs/diagnose/gate_ablation_nextframe.json
```

脚本按名字自动找 adapter 里所有标量 gate（`gate` / `fusion_gate` / `motion_gate`），所以
双 gate 的 `spatiotemporal_next_frame_motion` 也能用。分流消融同样按名字找
（`content_encoder` / `delta_encoder` / `displacement_projection`），用 `--streams` 控制，
默认 `content delta`。数据配置从 checkpoint 自己的 `hydra_config.yaml` 读，保证与训练时的
管线一致。

两个必须保留的实现细节：**forward 要包在 autocast 里**（`_keep_in_fp32_modules` 让 adapter
留在 fp32 而 backbone 输出 bf16，不加会直接报错，而强行统一 dtype 会评到一个数值上不同的
模型）；**gate 消融要看部分关闭那一档**（全关时两边都饱和到无条件语言模型的损失，差异被
压平）。

结果：`outputs/diagnose/gate_ablation_nextframe.json`（第 3 节）、
`outputs/diagnose/gate_ablation_nextframe_streams.json`（3.1 节，含全部五个条件）
