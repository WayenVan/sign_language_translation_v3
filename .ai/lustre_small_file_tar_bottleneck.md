# Lustre 小文件打包性能瓶颈：诊断与解决

日期：2026-09-22
节点：node02（Slurm job 1885419，21 CPU，376 GB 内存）
脚本：`scripts/pack_dir.sh`

## 背景

需要把 CSL-Daily 抽帧目录打成一个 tar：

- 源目录：`dataset/CSL-Daily-HG/preprocessed/full-trim-256x256px`（实际位于 `/mnt/scratch/...`，**Lustre**，stripe_count=1）
- 规模：约 2.06 万个 clip，平均每个 141 帧；**2,567,618 个文件**，每个 jpg 约 13 KB，合计约 35 GB
- 旧脚本：`tar -cf - DIR | zstd -T$(nproc) -3`，在 Slurm 上非常慢

## 结论（TL;DR）

- **瓶颈既不是 CPU，也不是压缩，而是 Lustre 上逐个读小文件的延迟。** 单个 tar 读一个文件要等 15–20 ms，只能串行等下去。
- 办法是**用 128 路并发预读，把数据和元数据灌进本节点的 page cache**，再让单个 tar 按同样的顺序从内存里读。
- 预计从 12–17 小时降到约 20 分钟，**快 30–40 倍**。
- jpg 本来就是压缩过的，所以不再用 zstd，直接输出 `.tar`。

## 瓶颈原因

在 Lustre 上读一个小文件，大致要经过这几步：

1. 向 MDS 发 `open` / `getattr`，拿到文件布局和锁
2. 向 OST 请求 glimpse 锁，确认文件大小
3. 向 OST 发 read RPC，取回数据

每一步都是一次网络往返。对 13 KB 的文件来说，真正传数据的时间几乎可以忽略，**耗时几乎全在往返延迟上**。

tar 是单线程的，每个文件都要按顺序做 `lstat → open → read → close`，同一时刻只有一个请求在路上。

我们在跑的 tar 进程上观察到：

- 状态是 `I`，`wchan = cl_sync_io_wait`，也就是一直卡在 Lustre 客户端的同步 I/O 等待里
- CPU 占用约 1%
- 从 `/proc/<pid>/io` 算出的读速率约 1 MB/s，大约每秒 70 个文件

所以旧脚本里 zstd 的线程数无论开多少都没有意义，因为它一直在等 tar 喂数据。

## 实验结果

每组实验都用**互不重叠**的 clip，避免 page cache 干扰结果。并行方式是 `xargs -P N` 起多个 `cat`，每个负责一个 clip 目录。

| 读法 | 文件/s | MB/s | 全量 256 万文件预计 |
|---|---|---|---|
| 单个 tar（旧脚本） | 47–70 | ~1 | 10–15 小时 |
| 并行 cat，P=8 | 341 | 4 | ~2 小时 |
| P=32 | 981 | 12 | ~45 分钟 |
| P=64 | 1610 | 19 | ~27 分钟 |
| **P=128** | **2273** | **28** | **~19 分钟** |
| P=256 | 2380 | 30 | 基本饱和，没再提升 |
| **P=128 预读 + 单个 tar 跟读** | **~2100** | **~23** | **~20 分钟** |

- 并发数从 1 加到 128，吞吐几乎是线性增长的，说明服务端完全扛得住，之前只是单个请求排队等延迟。
- 到 128 路左右就饱和了，这大概是这套 Lustre 对单个客户端的上限。
- "预读 + tar 跟读"的速度和纯并行读很接近，说明 tar 读的时候基本都命中了缓存。

**全量实跑结果**
- **总耗时 798 秒（约 13.3 分钟）**，其中列文件 9 秒
- 输出 `dataset/full-trim-256x256px.tar`，36,687,314,944 字节（34.2 GiB）；平均约 44 MB/s，约 3200 文件/s，比抽样测的还快
- 相比旧的单流 tar（预计 10–15 小时），**快了约 45–70 倍**
- 校验：`tar -tf` 列出 2,588,276 个条目，与 `find` 源目录得到的条目数（文件加目录）完全一致

## 解决方法（新 `pack_dir.sh`）

```bash
# 1. 遍历一次，生成两份顺序完全相同的 NUL 分隔列表
find "$NAME" -fprint0 all -type f -fprint0 files

# 2. 后台 128 路并发预读，内容直接丢弃，只为了把数据灌进缓存
xargs -0 -P 128 -n 32 cat < files > /dev/null &

# 3. 前台一个 tar，按同一顺序从缓存里读，写成单个 tar
tar -C "$PARENT" -b 512 --null --no-recursion -T all -cf out.tar
```

**第 1 步**
- `find` 对每个条目都会执行 `-fprint0 all`，所以 `all` 里是全部条目，包括目录，这样目录的元数据和空目录都能保留。
- 只有普通文件会通过 `-type f`，所以 `files` 里只有文件。
- 这一步只读目录，不打开文件，所以很快，全量只用了 9 秒。

**第 2 步**
- 每个文件**只读一遍**，起作用的是**并发**：128 个请求同时在路上，每个文件的等待时间就互相重叠了。
- 读过之后，文件内容进入 node02 的 page cache，Lustre 客户端也缓存了这个文件的锁和属性。
- 读失败的情况在这里直接忽略，因为 tar 之后会重新读每个文件，真有问题它会报错。

**第 3 步**
- tar 按和预读相同的顺序处理文件，读到某个文件时它通常已经在内存里了，每个文件的耗时从约 15 ms 降到微秒级。
- `--no-recursion` 是必须的：列表里已经有全部条目，不让 tar 自己再遍历目录，否则文件会被重复打包。
- `-b 512`：每次写 256 KiB，减少对 Lustre 的小块写入。

**其他细节**
- 输出先写到临时文件 `.pack.<pid>.<name>.tar`，成功后再 `mv` 成正式文件名；出错或被中断时，trap 会删掉临时文件并杀掉后台的预读进程。
- 用法：`scripts/pack_dir.sh [-P PREFETCH] [-f] SRC_DIR OUTPUT.tar`

## 注意事项 / 经验

- **前提是内存要放得下"预读领先 tar 的那部分数据"。** 这次数据约 35 GB，可用内存 342 GB，没有问题。如果目录比内存还大，预读可能跑得太靠前，缓存被挤掉，速度会下降，但结果依然正确。
- **最佳并发数取决于文件系统**，128 是在这套 `/mnt/scratch` Lustre 上测出来的。换环境时可以先用 `xargs -P N cat` 在不重叠的样本上扫一遍，找到拐点。
- **在已经压缩过的数据（jpg、mp4）上用 zstd 基本没有收益**，只会增加 CPU 开销。
- **测试时的坑**：
  - GNU tar 检测到输出是 `/dev/null` 时，会直接跳过读文件内容，测出来的速度是假的，要写成 `tar -cf - ... | cat > /dev/null`。
  - `pkill -f <pattern>` 可能会匹配到正在执行它的那个 shell 命令本身，把自己也杀掉，要改用 PID。
- **更根本的做法**：训练时尽量不要在 Lustre 上直接读几百万个小文件。可以像这次这样打成 tar，再拷到节点本地盘解压，或者直接用分片格式（比如 WebDataset 的 tar shard）读取。
