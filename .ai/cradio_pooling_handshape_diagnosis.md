# 池化方式与手型信息诊断

日期：2026-09-01

前置：`.ai/cradio_patch_separability_diagnosis.md`。那份诊断的结尾留了一个缺口——
「patch 特征能分出**是不是**手，但能不能分出**是哪个**手型？」——本文档回答它，
并顺带回答了一个更要命的问题：**手型信息在 adapter 的池化环节就已经归零了。**

## 结论先行

1. **当前架构（全局均值池化）传给 LLM 的手型信息是 0，不是少。** 手部包围盒硬裁剪能拿到
   R² = 0.594（手型+朝向），全局均值 = **−0.009**。这不是信噪比问题，是信息在 adapter
   里被删干净了，**LLM 后面无论怎么微调都恢复不了**。
2. **空间网格和软加权都救不回来，只有硬裁剪有效。** 6 区域网格 0.080，运动加权 0.033，
   冻结手部打分器加权 0.081——对比硬裁剪的 0.594，差一个数量级。软权重再尖锐，也会把另外
   ~170 个非手 patch 的内容混进同一个向量，而手型是高频细节，一平均就没了。
3. **分辨率是二阶效应。** 224 → 512（patch 网格 14×14 → 32×32，手覆盖的 patch 从 26 涨到
   119）只把纯手型从 0.19–0.22 提到 0.23–0.26，代价是 backbone FLOPs 涨 5.2×。
   **池化方式带来 0.70 的差距，分辨率带来 0.07，相差 10 倍。** 优先级应该反过来。

## 1. 实验设置

| 项 | 值 |
| --- | --- |
| 特征 | `outputs/diagnose/features.npz`（224，27 层，14×14=196 patch）复用，未重跑 backbone |
| 新增特征 | `outputs/diagnose/features512.npz`（512，层 `[-6,-3,-1]`，32×32=1024 patch） |
| 样本 | 与前次诊断**完全相同**的 40 个 val 视频 × 6 帧 = 240 帧 |
| 手部标注 | MediaPipe Hand Landmarker，21 关节，在 512 上采样图上检测；**221/240 帧**检出至少一只手，159 帧检出两只 |
| 探针 | PCA→48 维 + Ridge；外层 `GroupKFold(4)` 按 video 分组，内层 `GroupKFold(3)` 选 alpha ∈ {1, 10, 10², 10³, 10⁴} |
| 脚本 | `experiments/diagnose/handshape_probe.py` |
| 关节缓存 | `outputs/diagnose/hand_landmarks.npz`（探针脚本首次运行时自动生成） |

**帧一致性校验**（A/B 成立的前提）：512 的帧下采样回 224 后与原缓存
`mean |Δ| = 0.36/255`，`corr = 0.9999`，`video_ids` 完全相同。两次抽取看到的是同一批帧。

512 抽取用的 hydra override（没有单独提交脚本，照抄 `extract.py` 的 loader 再加这几条即可；
seed、视频数、抽帧逻辑都必须与 `extract.py` 保持一致，否则帧对不上）：

```
model=qwen3-4b-cradio-l-spatiotemporal-pooled-linear
data.processor.video_processor.do_normalize=false
data.processor.video_processor.do_resize=true
data.processor.video_processor.size.height=512
data.processor.video_processor.size.width=512
+data.processor.video_processor.resample=3
```

### 1.1 目标的三种归一化

关节坐标直接回归等于在测「手在哪」，必须把位置和尺度剥掉：

| 目标 | 构造 | 测的是什么 |
| --- | --- | --- |
| `position` | 21 个关节的图像坐标质心 | **对照组**。这一项不接近 1 就说明管线坏了，不是特征的问题 |
| `shape+orient` | 关节减腕点、除以 腕→中指MCP 距离（40 维） | 手型 + 手的朝向 |
| `shape only` | 再旋转到 腕→MCP 固定方向 | **纯手指构型** |

### 1.2 位置先验地板

手语里手型和位置强相关（某些手型只在某些位置出现），所以「只用手的位置预测手型」这条
地板线必须先量出来，**只有超出它的部分才是特征真的编码了手型**：

| 目标 | 仅用位置的 R² |
| --- | ---: |
| `shape+orient` | 0.283 |
| `shape only` | **0.051** |
| `position`（自回归，健全性检查） | 0.965 |

## 2. 手型确实被编码，但很弱，且集中在末层

输入 = 手部包围盒覆盖的 patch 均值（224 下平均 26/196 个 patch）：

| block | `shape+orient` | `shape only` | `position`（对照） |
| ---: | ---: | ---: | ---: |
| -27 | 0.342 | 0.032 | — |
| -24 | 0.399 | 0.084 | — |
| -21 | 0.489 | 0.108 | — |
| -18 | 0.459 | 0.124 | — |
| -15 | 0.489 | 0.145 | — |
| -12 | 0.511 | 0.157 | — |
| -9 | 0.570 | 0.150 | — |
| -6 | 0.610 | 0.194 | — |
| **-3** | **0.636** | **0.215** | 0.967 |
| -2 | 0.620 | 0.210 | 0.968 |
| -1 | 0.595 | 0.189 | 0.949 |

两点：

- **单调向末层升高**，与前次诊断「末层强化部位语义」一致，`output_layer: -1` 再次得到支持
  （-3 略优于 -1，差距 0.04，不足以改配置）。
- **`shape+orient` 0.64 而 `shape only` 只有 0.22**。差出来的这一大截是**朝向**。
  也就是说：C-RADIO 在 224 下把手的**位置（0.97）和朝向（~0.4 的增量）**编码得很好，
  **手指构型（0.22，地板 0.05）编码得很差**。前次诊断怀疑「手型才是真瓶颈」——证实了。

---

## 3. 核心结果：池化方式决定一切

layer -1，同一套目标、同一套折划分，只改池化方式：

| 每帧 token | 池化 | `shape+orient` | `shape only` | `position` |
| ---: | --- | ---: | ---: | ---: |
| 1 | **手部包围盒（硬裁剪）** | **0.594** | **0.189** | 0.947 |
| 1 | **全局均值（当前架构）** | **−0.009** | **−0.007** | 0.175 |
| 6 | 空间网格 3×2 | 0.091 | 0.012 | 0.364 |

**全局均值不仅把手型删干净了，连手的位置都只剩 0.175**（硬裁剪 0.947）。
196 个 patch 平均成一个向量之后，剩下的基本是「这一帧整体长什么样」。

### 3.1 软加权同样无效（打分器无泄漏，只在训练折上拟合）

| 每帧 token | 池化 | `shape+orient` | `shape only` |
| ---: | --- | ---: | ---: |
| 1 | 全局均值 | −0.012 | −0.007 |
| 6 | 空间网格 3×2 | 0.080 | 0.008 |
| 2 | 全局 + 运动加权（`motion` layer -21，softmax） | 0.033 | 0.024 |
| 2 | 全局 + 冻结手部打分器加权（`Linear(1152→1)`，只用训练折视频的 MediaPipe 标签拟合） | 0.081 | 0.046 |

即使用前次诊断里 AUC = 1.000 的那个手/脸打分器做 softmax 权重，也只到 0.081。
**结论是硬的：要保住手型，必须是 hard selection / crop，不能是 soft weighting。**

### 3.2 一个早期的代理指标给出了误导性结论，已作废

在拿到真实手型标签之前，我们先用两个代理目标（手部 patch 质心位置、手部 patch 均值特征的
前 16 个 PCA 分量）比较过池化方案，结论是「6 区域 ≈ 2-token 软加权 ≈ 0.55，都远好于全局
均值 0.26/0.43」：

| 每帧 token | R² 手部位置（代理） | R² 手部外观（代理） |
| ---: | ---: | ---: |
| 1（全局均值） | 0.260 | 0.426 |
| 4（2×2） | 0.495 | 0.553 |
| 6（3×2） | 0.541 | 0.565 |
| 9（3×3） | 0.457 | 0.502 |
| 16（4×4） | 0.360 | 0.330 |
| 2（全局 + 运动加权） | 0.213 | 0.561 |

**换成真实手型目标后这个排序不成立**（6 区域掉到 0.09/0.01，软加权掉到 0.03/0.02）。
教训：「手部 patch 均值特征」这个代理目标里混着大量位置和整体外观信息，会把一个对手型
毫无用处的池化方案打成及格。**代理目标只能用来排除方案，不能用来选方案。**

同一批实验里还有一行「全局 + 真实手部均值(oracle)」拿到 0.911/0.979，**这个数是循环的**
（输入就是目标的来源），不能当上界，已作废。

## 4. 分辨率 A/B：224 vs 512

同一批帧、同一套目标、同一份探针代码，只改 backbone 输入尺寸：

| 输入 | 手部包围盒占比 | block | `shape+orient` | `shape only` | `position` |
| --- | --- | ---: | ---: | ---: | ---: |
| **512**（32×32=1024） | 119 patch / 11.6% | -6 | 0.629 | **0.264** | 0.977 |
| | | -3 | **0.702** | 0.251 | 0.980 |
| | | -1 | 0.685 | 0.233 | 0.955 |
| **224**（14×14=196） | 26 patch / 13.2% | -6 | 0.611 | 0.191 | 0.963 |
| | | -3 | 0.637 | 0.218 | 0.967 |
| | | -1 | 0.590 | 0.188 | 0.947 |

池化对比在 512 下同样不变：

| 输入 | layer -1 池化 | `shape+orient` | `shape only` | `position` |
| --- | --- | ---: | ---: | ---: |
| 512 | 全局均值 | 0.001 | −0.007 | 0.168 |
| 512 | 6 空间区域 | 0.106 | 0.020 | 0.365 |
| 224 | 全局均值 | −0.009 | −0.007 | 0.175 |
| 224 | 6 空间区域 | 0.091 | 0.012 | 0.364 |

三点：

- **提升真实但很小。** 6 个对比（3 层 × 2 个手型目标）**全部为正**，所以不是噪声；
  但纯手型只从 0.19–0.22 到 0.23–0.26，即 +0.03~0.07。
- **代价 5.2×**（1024 vs 196 个 token 过 backbone）。为 +0.04 付 5 倍算力不划算。
- **天花板在源像素。** `Ph14TGeneralDataset` 读的是 release 的 `fullFrame-256x256px`
  变体（它本身是从原始 210×260 采集帧生成的），eval 变换是 224×224 中心裁剪**且不缩放**。
  所以链路是 `210×260 采集 → 256×256 → 224 裁剪 → 512 插值`：**512 那一步不含任何新的
  像素细节**，测的是 **patch 粒度**。手覆盖的 patch 涨了 4.6× 而纯手型只涨 0.04，说明粒度
  已经不是限制项了。**在这个数据集上「提分辨率」这条路到头了**——真正的光学上限是 210×260
  的采集分辨率，不是任何一级重采样。
- **512 没有救活全局均值**（还是 0.00）。把分辨率提上去再全局平均，等于把更多细节倒进
  同一个漏斗。

## 5. 对设计的结论

1. **不要做每帧 N 个空间区域 token。** 两个分辨率下都是 ~0.09 / ~0.01，而代价是序列长度
   ×N、CTC 对齐要重做、小数据（~7k 训练视频）下更难学。**收益接近零，代价确定。**
2. **要做就做 hand-ROI 硬裁剪 token。** 这是唯一有数量级收益的形态（0.59–0.70 vs 0.00）。
   定位器用前次诊断验证过的两条路：帧间运动打分器（手召回 0.81 @ k=32），或用 MediaPipe
   标签离线拟合并**冻结**的 `Linear(1152→1)`（手/脸 AUC 1.000，训练时零可训练参数）。
   token 只涨 2–3×，CTC 基本不用动。
3. **别做全帧 512。** 想要手部的有效分辨率，正确做法是**把 ROI 从原始帧裁出来单独送 backbone**：
   手只占画面 ~12%，用 224 的预算裁一个手部 ROI，手上的有效分辨率比全帧 512 更高，算力反而更省。
4. **调整对「手型」的预期。** 纯手指构型即使在最好条件下（512 + 硬裁剪）也只有 0.26，
   而**位置 0.98、朝向贡献约 0.45** 编码得很好。位置和朝向本身就是手语的主要音位参数——
   与其继续追手指细节，不如让 adapter 把确实存在的位置/朝向/运动完整送出去，
   而这正是 hard-crop ROI token 能做、全局均值做不到的事。
5. **`output_layer: -1` 维持不变**（-3 略优 0.04，不值得改）。

## 6. Caveats

- **样本量小。** 221 帧 / 40 视频对 40 维目标，单点 R² 的噪声约 ±0.03–0.05。
  所以第 4 节看的是「6 个对比方向一致」，而不是任何单个数字。
- **`shape only` 是下界，不是真值。** MediaPipe 是在 224 裁剪帧上采样到 512 做的检测，
  手指关节坐标本身带噪声，**目标噪声直接压住 R² 上限**。0.26 不能读成「特征里只有 26%
  的手型信息」。要拿到干净目标得在原始视频帧上重跑关节检测。
- **512 是插值，不是更高的源分辨率。** 见第 4 节。这条结论不能外推到有高清源的数据集。
- **只用了较大的那一只手。** 双手同时出现的 159 帧里，另一只手完全没进探针。
- **全是单帧诊断。** 运动信息怎么和 ROI token 结合，本文档没有测。
- 早期代理指标那一轮里，k=196（全 patch 展开）出现 −0.57 / −0.84 的负 R²，
  那是 221 样本撑不住 225,792 维的小样本假象，不是信息真的变少。

---

## 7. 本次诊断没有回答的问题

- **hard-crop ROI token 的端到端收益。** 探针说信息在，但没测它在真实训练里换来多少 BLEU。
- **定位误差的影响。** 本文档的 ROI 用的是 MediaPipe 真值框；换成运动打分器或冻结探针
  定位后，框会抖、会漏，ROI token 的 R² 会掉多少未知。
- **双手怎么处理。** 一个 ROI token 还是两个？非惯用手要不要单独给 token？
- **干净目标下的手型上界。** 在原始视频帧（而非 224 裁剪）上重跑 MediaPipe，
  `shape only` 的天花板会抬到哪里。
- **时间维。** ROI token 和 `NextFramePatchFusion` / 运动残差怎么组合。
